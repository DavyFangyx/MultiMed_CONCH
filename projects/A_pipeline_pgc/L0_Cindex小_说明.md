结论:不是字段没对齐,编码管线与原始文件是 1:1 对齐的

我把「L0粉干」理解为 L0 分数(即 L0Test 表里 C 行 clinic-only 模型的数值)。小是真小,但原因不是对齐问题,而是 L0 这套字段本身对 coad/lihc 几乎没有预后信息量。

1. L0 是什么

A_pipeline_pgc/templates/schemes.json → templates/L0/fields.json,L0 = 只有 4 个人口学字段:

2. 对齐核查:原始文件 → prompt → embedding,全部对得上

对照原始文件(A_pipeline_pgc/datasets.json 里登记的 lizhe cart):

- COAD 源文件 TCGA-COAD/Bulk_RNA_cases/clinical.cart.2026-06-18.json:458 例,与 prompts.csv 的 458 行一致;age/sex 填充率 ~100%
- LIHC 源文件 TCGA_LIHC/clinical/clinical.cart.2026-06-01.json:365 例,365/365 一致
- 逐例抽查:原始 JSON 里的 age/sex/race/ethnicity 值 → prompt 句子,6 例全对(含 "Race is not reported." 的忠实传递)
- embedding 产物:所有数据集统一 (4, 512)、范数 2.0(coad/lihc 与 brca/kirc/luad 完全一致),没有任何数值层面的"小"或退化

唯一值得注意的原始数据事实:COAD 的 race/ethnicity 在源头就有 38%/40% 是 "not reported"(GDC 原始缺省),管线只是如实编码了。这是数据本身缺,不是抽取丢。

4. 两个补充提醒

1. kirp 其实比 coad/lihc 还小(L0Test C 行 0.4585/0.5137),如果你按"L0 分数小"筛数据集,kirp 也在同一组。
2. coad 的 G(基因)行也是 7 数据集里最低的(0.483/0.486),这与 L0 无关——coad 这一列整体偏难,但 Ours 行 0.6945(1) 不受影响。另外这三份变体(BeforeTune/L0Test/AfterFix)里 C/G 行的值完全相同,因为它们是共享的 baseline 训练结果,不是训练噪声。
